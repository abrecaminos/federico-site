About me

I didn't start out in tech. I studied Economics, got interested in film, and ended up with a degree in Sworn Translation from Universidad del Salvador. Translation taught me to read for exact meaning, and that turned out to be a big part of this job.

Before moving fully into documentation, I worked as a localization Project Manager, coordinating translators, quality control, client communication and delivery dates. That experience shapes how I plan documentation work across teams today, from tracking dependencies to spotting gaps before a release.

My interest in software documentation started while I was studying Android development. I wrote guides for myself as I went, other students started using them, and then the instructors adopted them too. Later, my first technical writing work was documenting quantitative financial models for Wells Fargo. I had to learn the math from scratch so I could work with the analysts, and every document went through internal model validation.

Since then I've documented marketing automation, travel, logistics and restaurant technology products. I've often been the only writer, or the most senior one, on the team. Outside work I wrote a Flutter reference in Spanish, answered questions on Stack Overflow, and co-organize a small technical-writing group in Buenos Aires with another writer.

Writing sample · fictional API

Submit your first sandbox order

A short integration guide for a fictional restaurant ordering API: prerequisites, a request, an expected response and recovery steps.

Hide the guide

Demonstration only. This API is invented and example.com is a reserved placeholder host, so these requests can't run against a real service.

Goal

Create a sandbox order and retrieve its status. Sandbox orders don't reach a restaurant or trigger a payment.

Before you begin

  • A sandbox access token with orders:write and orders:read permissions.
  • A sandbox location ID and an available menu-item ID for that location.
  • cURL in a Bash-compatible terminal. Replace the placeholders with your sandbox values.

1. Configure the request

export BASE_URL='https://sandbox.example.com/v1'
export API_TOKEN='YOUR_SANDBOX_TOKEN'
export LOCATION_ID='YOUR_LOCATION_ID'
export ITEM_ID='YOUR_MENU_ITEM_ID'
export ORDER_KEY='demo-order-001'

Use a new ORDER_KEY for each new order. Reuse the same key and request body only when retrying an order whose response was lost.

2. Create the order

curl --include --request POST "$BASE_URL/orders" \
  --header "Authorization: Bearer $API_TOKEN" \
  --header 'Content-Type: application/json' \
  --header "Idempotency-Key: $ORDER_KEY" \
  --data @- <<EOF
{
  "location_id": "$LOCATION_ID",
  "items": [{ "item_id": "$ITEM_ID", "quantity": 1 }],
  "fulfillment_type": "pickup"
}
EOF

Expected response: 201 Created. Save the returned id for the next request. A created order doesn't yet mean a restaurant has accepted it.

{
  "id": "ord_demo_001",
  "status": "received",
  "location_id": "loc_demo_001",
  "fulfillment_type": "pickup"
}

3. Retrieve the order

export ORDER_ID='ord_demo_001'  # Replace with the returned id
curl --include "$BASE_URL/orders/$ORDER_ID" \
  --header "Authorization: Bearer $API_TOKEN"

Expected response: 200 OK, with the same order ID and its current status.

Troubleshooting

  • 401 Unauthorized: check that the token is present, valid and issued for the sandbox environment.
  • 403 Forbidden: confirm the token has the required permissions and access to the location.
  • 404 Not Found on retrieval: verify the order ID and that you're calling the sandbox environment.
  • 409 Conflict: the idempotency key was reused with a different body. Restore the original body to retry, or use a new key for a separate order.
  • 422 Unprocessable Content: read the error response for the invalid field. Confirm the item belongs to the location and the quantity is a positive integer.
  • Timeout after submitting: retry with the same body and the same idempotency key. A matching retry returns the existing order instead of creating a new one.

Why the guide is structured this way

Prerequisites make dependencies explicit. The request and response give a success condition the reader can check. Idempotency and error guidance cover what a developer needs when the happy path fails.

API documentation verified against the real API

The challenge

Ran every API flow in Postman before publishing. When the behavior didn't match the spec, I corrected the OpenAPI files in the code repositories and reviewed the changes with the Integrations team. I tested product workflows, took part in QA and UAT, and reported defects in Jira.
What I delivered
OpenAPI-based API references, integration guides, release notes and an API portal kept in sync with the code. I also used Python and AI-assisted workflows to automate recurring maintenance and support content reviews.
